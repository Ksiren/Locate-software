# Locate-software

REST API бюро находок: сотрудник регистрирует вещь, пользователь подаёт заявку,
ответственный сотрудник принимает решение и оформляет выдачу.

Сейчас реализована запускаемая основа для EK1: `GET /health` отвечает
HTTP 200 и `{"status":"ok"}`. Это проверка работы HTTP-сервиса.
Предметные сценарии, аутентификация и PostgreSQL пока не реализованы.

Документы: [паспорт проекта](PROJECT.md),
[требования безопасности](SECURITY_REQUIREMENTS.md),
[использование ИИ](AI_USAGE.md).

## Локальный запуск

Нужны Python 3.12 или новее, pip и curl. Команды выполняются из корня
репозитория. Установка, запуск и проверки выполнены на macOS с Python 3.14.6.
Для установки зависимостей нужен доступ к PyPI;
для самого запуска БД, облако и внешние сервисы не требуются.

Команды для macOS/Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -c requirements.lock -e ".[dev]"
python -m uvicorn locate.bootstrap:create_app --factory --host 127.0.0.1 --port 8000
```

В другом терминале:

```bash
curl -i http://127.0.0.1:8000/health
```

Ожидаемый ответ (заголовки даты и сервера могут отличаться):

```http
HTTP/1.1 200 OK
content-type: application/json

{"status":"ok"}
```

Остановить сервер: `Ctrl+C` в терминале с Uvicorn.
Сервис слушает только локальный интерфейс `127.0.0.1`.
Swagger UI доступен по адресу <http://127.0.0.1:8000/docs>.

## Проверки

Из корня репозитория с активированным `.venv`:

```bash
python -m pip check
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

Ожидается: совместимые зависимости, один пройденный тест и отсутствие ошибок Ruff.
[HTTP-тест](tests/api/test_health.py) проверяет статус, Content-Type и точный JSON
через собранное приложение. Реальный запуск Uvicorn проверяется запросом выше.
Эти проверки не подтверждают выполнение требований безопасности.

[Ruff](https://docs.astral.sh/ruff/) проверяет Python-код: например, находит
неиспользуемые импорты и проверяет форматирование. Он входит только в зависимости
для разработки (`dev`); для работы API не нужен.

[Starlette](https://fastapi.tiangolo.com/features/#starlette-features) - библиотека,
на которой построен FastAPI: маршрутизация, запросы, ответы и тестовый клиент.
Она устанавливается вместе с FastAPI, отдельно запускать или настраивать её не нужно.
Для TestClient установлен `httpx2`, рекомендованный в [документации Starlette](https://starlette.dev/testclient/).

Для фиксации демонстрируемой версии используйте `git rev-parse HEAD`;
`git status --short` должен быть пустым. Прямые зависимости заданы в
`pyproject.toml`; полный набор, включая транзитивные, зафиксирован в `requirements.lock`.
При обновлении зависимостей нужно согласованно обновить оба файла и повторить проверки.

## Архитектура

Один сервис с разделением по Clean Architecture. На первом шаге существуют
только сборка приложения и HTTP-адаптер:

```text
src/locate/
  bootstrap.py                 # create_app: сборка приложения
  presentation/api/
    routes.py                  # HTTP-маршруты
    schemas.py                 # Pydantic-схемы ответов
tests/api/test_health.py        # проверка HTTP-контракта
```

Uvicorn вызывает `create_app`, фабрика подключает маршруты, обработчик `/health`
возвращает ответ по схеме `HealthResponse`. Этот маршрут не читает данные и
не требует предметного сценария или репозитория.

С первым сценарием чтения каталога появятся остальные слои:

| Слой | Содержание | Разрешённые зависимости внутри проекта |
| --- | --- | --- |
| `domain` | Вещи, заявки, выдачи и предметные правила | Нет |
| `application` | Сценарии, политика доступа, DTO и порты хранилища | `domain` |
| `infrastructure` | PostgreSQL, SQLAlchemy, реализация портов и транзакций | `application`, `domain` |
| `presentation` | HTTP-маршруты и Pydantic-схемы | `application` |
| `bootstrap` | Создание конкретных зависимостей и передача их сценариям | Внешние и внутренние слои |

Предметные объекты и DTO будут обычными Python-типами. Внутренние слои не
импортируют FastAPI, Pydantic или SQLAlchemy; ORM-модели не попадают прямо в ответ.
Права проверяет сценарий по установленной сервером личности, роли и владельцу
записи. HTTP-слой отвечает за формат запроса и преобразование результата.

Следующий шаг - чтение открытого каталога из локального PostgreSQL через сценарий
и порт репозитория. Защищённые операции добавляются после аутентификации.
Для синхронной работы с БД планируются обработчики `def` и отдельная Session
на операцию; выдача потребует транзакции и защиты от конкурирующих изменений в БД.
CLI и размещение в Yandex Cloud не нужны для запуска этой версии.
