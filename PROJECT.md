## 1. Назначение

Сервис позволяет сотрудникам бюро находок "Потеряшки" вести учет найденных вещей, хранящихся на складе. Люди, потерявшие вещь, могут найти ее на сайте. Для каждой вещи хранятся описание, место и время обнаружения, заявки на получение, решения по ним и сведения о выдаче. Сотрудник проверяет принадлежность вещи по сведениям заявителя и скрытым признакам предмета. Сервис связывает выдачу с одобренной заявкой и не допускает повторной выдачи одной вещи.

## 2. Граница продукта

**В продукт входит:**

- Один сервис на Python с REST API и хранением данных в PostgreSQL;
- Учет найденных вещей: открытое и скрытое описание, место и время обнаружения, текущее состояние;
- Обработка заявок на получение вещи, сохранение решения сотрудника и учет выдачи конкретному получателю;
- Вход в систему и разграничение действий и видимости данных по ролям. Сервер обрабатывает параллельные запросы безопасно;
- Простой CLI-клиент на Python для обращения к API (опционально).

**Внешнее окружение и внешние системы:**

- Yandex Cloud - планирумая площадка для размещения (для разработки запуск локальный);
- Компьютеры пользователей и сотрудников, с которых выполняются запросы;
- Бюро находок, где сотрудники принимают, хранят и передают вещи.

**Команда сознательно не реализует:**

- Веб-интерфейс и мобильное приложение;
- Автоматическое определение владельца (решение верификации остается за сотрудником);
- Доставку вещей, платежи и интеграцию с внешними базами розыска.

## 4. Сквозные сценарии

### Сценарий 1. Прием и регистрация найденной вещи

- **Участники:** человек, принесший находку и сотрудник бюро находок.
- **Начальное условие:** найденную вещь принесли в бюро находок; записи о ней в системе еще нет.
- **Основные действия:** сотрудник принимает вещь и входит систему. Указывает место и время обнаружения, открытое описание для поиска и скрытые признаки для последующей проверки принадлежности (опционально, данные человека, нашедшего вещь). Сервис сохраняет карточку о товаре, и делает доступным ее открытое описание.
- **Результат:** вещь принята на хранение и учтена; потерявший ее человек может найти запись в каталоге.
- **Какие данные или состояние изменяются:** создается карточка вещи с описанием, местом и временем обнаружения, скрытыми признаками. Состояние вещи "на хранении".

### Сценарий 2. Поиск вещей и подача заявки

- **Участники:** пользователь, потерявший вещь.
- **Начальное условие:** вещь зарегистрирована в каталоге и ещё не выдана.
- **Основные действия:** пользователь ищет вещь по открытым данным и выбирает подходящую карточку. Входит в систему, указывает сведения о себе и признаки, подтверждающие принадлежность вещи, затем подаёт заявку. Сервис связывает заявку с пользователем и вещью; пользователь может просмотреть свою заявку и её состояние.
- **Результат:** обращение о возврате вещи зарегистрировано и доступно ответственному сотруднику для рассмотрения.
- **Какие данные или состояние изменяются:** создаётся заявка со сведениями о заявителе и подтверждением принадлежности. Вещь остаётся на хранении.

### Сценарий 3. Рассмотрение заявки и возврат вещи

- **Участники:** заявитель и ответственный сотрудник.
- **Начальное условие:** заявка ожидает рассмотрения, вещь находится на хранении.
- **Основные действия:** ответственный сотрудник сопоставляет сведения заявителя со скрытыми признаками вещи и сохраняет решение. Если принадлежность подтверждена, одобряет заявку. При получении вещи заявителем сотрудник передаёт её и фиксирует выдачу по одобренной заявке; сервис сохраняет получателя, сотрудника и время выдачи. Если принадлежность не подтверждена, сотрудник отклоняет заявку с указанием причины. Заявитель видит решение в своей заявке.
- **Результат:** вещь возвращена подтверждённому владельцу либо заявитель получил отказ, а вещь осталась на хранении. Одобрение заявки само по себе не означает выдачу.
- **Какие данные или состояние изменяются:** сохраняется решение, заявка становится одобренной или отклонённой. При выдаче создаётся связанная с заявкой запись, вещь переходит в состояние «выдана» и становится недоступной для повторной выдачи.

## 6. Компоненты и внешние взаимодействия

Делаем один сервер на Python с REST API и базой PostgreSQL. Внутри сервера разделяем обработку запросов, логику работы с вещами и заявками и доступ к базе по принципам Clean Architecture.

- **Сервер** принимает запросы, проверяет входные данные и права пользователя. Через него сотрудники регистрируют находки, пользователи подают заявки, а ответственный сотрудник принимает решение и оформляет выдачу.
- **PostgreSQL** хранит пользователей и роли, открытые и скрытые описания вещей, заявки, решения и сведения о выдаче. К базе обращается только сервер. Связанные изменения выполняются в транзакциях, чтобы параллельные запросы не привели к повторной выдаче одной вещи.
- **CLI-клиент на Python** отправляет запросы к API и показывает ответы в консоли. Если не успеем его сделать, к API можно обращаться через HTTP-клиент.

Схема взаимодействия: клиент → REST API → логика сервера → PostgreSQL. В запросах передаются параметры поиска, данные находок, заявки и решения. В ответах сервер возвращает только те данные, которые доступны конкретному пользователю.

Граница доверия проходит между клиентом и сервером: переданные клиентом данные нужно проверять. Роль пользователя и владельца заявки сервер определяет по данным аутентификации и базы.

Для размещения планируем Yandex Cloud, но сервер и база должны работать и локально. Отдельные фоновые процессы и интеграции с внешними системами пока не планируем.

## 8. Минимальное функциональное ядро

**Обязательные функции:**

- Вход в систему и разделение прав. Сотрудник регистрирует вещи, ответственный сотрудник рассматривает заявки и оформляет выдачу, пользователь работает со своими заявками. Без входа можно смотреть открытый каталог.
- Регистрация и редактирование находки: открытое описание, скрытые признаки, место и время обнаружения, состояние вещи. Скрытые признаки не должны попадать в открытый каталог.
- Поиск и просмотр вещей по открытым данным.
- Подача заявки со сведениями о заявителе и признаками, подтверждающими владение вещью. Пользователь может смотреть свою заявку и редактировать её до принятия решения.
- Рассмотрение заявки ответственным сотрудником. Он сравнивает сведения заявителя со скрытыми признаками и сохраняет решение: одобрить или отклонить.
- Выдача вещи по одобренной заявке. Сохраняем получателя, сотрудника и время выдачи, а вещь переводим в состояние «выдана». Если два запроса на выдачу приходят одновременно, успешно завершиться может только один. Одобрение заявки ещё не означает, что вещь выдана.
- Хранение данных в PostgreSQL, чтобы они сохранялись после перезапуска сервера.

Так остаются три основных сценария: сотрудник регистрирует находку; пользователь находит её и подаёт заявку; ответственный сотрудник рассматривает заявку и возвращает вещь. Права доступа и допустимость изменения статусов проверяются на сервере.

**Функции, которые можно исключить при нехватке времени:**

- CLI-клиент — запросы можно отправлять напрямую к REST API.
- Фотографии вещей — на первом этапе достаточно текстового описания и скрытых признаков.
- Расширенные фильтры — оставляем поиск по открытому описанию.
- Размещение в Yandex Cloud — для запуска достаточно локального сервера и базы.

Это ядро итогового продукта. К EK1 сначала готовим минимальную запускаемую основу; все сценарии на этом этапе реализовывать не требуется.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Python, REST API, JSON и PostgreSQL. Делаем один сервис с разделением API, логики приложения и работы с базой по принципам Clean Architecture. Веб-фреймворк и библиотеку для PostgreSQL ещё нужно выбрать. CLI, если успеем его добавить, тоже пишем на Python.

**Технологии, новые для команды:** нужно уточнить у участников, с чем они уже работали. Пока эта информация не собрана.

**Внешние сервисы, необходимые для запуска:** для локальной версии облачные сервисы не нужны. Нужны Python и локальная PostgreSQL. Yandex Cloud планируем использовать для размещения позже.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** запускаем сервер и базу локально, отправляем запросы через HTTP-клиент или CLI. На тестовых учётных записях разных ролей проверим регистрацию находки, поиск, подачу и рассмотрение заявки, выдачу вещи. Также проверим попытки открыть чужую заявку, получить скрытые признаки и повторно выдать вещь. Эти проверки пока запланированы.

**Что команда реализует первым, чтобы получить запускаемую версию:** небольшой сервер с `GET /health`. Планируемый ответ — HTTP 200 и JSON `{"status": "ok"}`. Добавим исходный код, зависимости и инструкцию с командами запуска и проверки. После этого подключим PostgreSQL и начнём добавлять основные функции.
