# Подготовка к защите Locate

Материал для объяснения проекта, вклада M3 и цепочки безопасности выдачи. Основные документы: [паспорт](../PROJECT.md), [требования](../SECURITY_REQUIREMENTS.md), [модель угроз](../THREAT_MODEL.md), [решения](../SECURITY_DECISIONS.md) и [вклад участников](../CONTRIBUTIONS.md).

## Текущее состояние

Locate — REST API бюро находок. Сотрудник регистрирует вещь, пользователь подаёт заявку, ответственный сотрудник проверяет принадлежность и оформляет выдачу.

| Часть | Реализовано | Планируется |
| --- | --- | --- |
| API | GET /health, автоматическая документация FastAPI | Каталог, заявки, решения и выдача |
| Данные | Pydantic-схема HealthResponse | Пользователи, вещи, заявки и выдачи в PostgreSQL |
| Доступ | Предметных защищённых операций нет | Токен, проверки роли, автора и разрешённых полей |
| Архитектура | Сборка приложения и HTTP-адаптер | Сценарии приложения, предметные правила и работа с базой |
| Проверки | Один тест /health и реальный запуск Uvicorn | Проверки прав, конкуренции и отката |

Результаты запуска приведены в [локальной проверке](LOCAL_VALIDATION.md). Успешный /health подтверждает работу HTTP-сервера; безопасность будущих операций проверяется отдельно.

## Часть M3 в паспорте

**Раздел 6 — компоненты.** Клиент отправляет запрос к серверу. Сервер проверяет данные и права, выполняет сценарий, обращается к PostgreSQL и возвращает разрешённые данные. Клиент не имеет прямого доступа к базе. Переданным идентификаторам и полям нельзя доверять даже после входа пользователя.

**Раздел 8 — минимальное ядро.** Обязателен полный путь от регистрации находки до возврата: открытый каталог, заявка, решение сотрудника, выдача, права доступа и хранение данных. CLI, фотографии, расширенные фильтры и облако можно отложить.

**Раздел 9 — стек.** Python — язык, FastAPI — обработка HTTP-запросов, Uvicorn — сервер, Pydantic — структура и проверка данных. PostgreSQL хранит записи, SQLAlchemy будет использоваться для работы с базой. Две последние технологии пока не подключены.

Одобрение заявки и выдача — разные события. Одобрение подтверждает решение сотрудника; выдача фиксирует передачу вещи получателю.

## Требования выдачи

| Требование | Правило | Проверка |
| --- | --- | --- |
| SR-ISS-01 | Ответственный сотрудник выдаёт по одобренной заявке на эту вещь; получатель из заявки | Подходящий запрос проходит, неверная заявка и запрещённая роль отклоняются без изменений |
| SR-ISS-02 | Не более одной выдачи на вещь; получатель после выдачи не меняется | Повтор отклонён; из двух одновременных допустимых запросов без искусственных сбоев успешен один |
| SR-ISS-03 | Выдача и состояние вещи сохраняются вместе | Ошибка до commit не оставляет частичных данных; успешный результат сохраняется после перезапуска |

Требование задаёт нужное свойство системы. Угроза описывает сценарий его нарушения. Решение объясняет механизм защиты, а критерий приёмки и план проверки — как оценить результат.

## Основная цепочка

[T-ISS-02](../THREAT_MODEL.md#t-iss-02) → [SR-ISS-02](../SECURITY_REQUIREMENTS.md#sr-iss-02) → [D-ISS-01](../SECURITY_DECISIONS.md#d-iss-01) → [CHECK-ISS-02](../SECURITY_DECISIONS.md#check-iss-02).

**Угроза.** Два запроса одновременно прочитали состояние «на хранении». Каждый решил, что выдача разрешена. Без координации оба могут сохранить выдачу.

**Требование.** Для одной вещи сохраняется не более одной выдачи. Повторы и конкуренция не меняют получателя.

**Решение.** В транзакции PostgreSQL сервер блокирует строку вещи, затем заявки. Под блокировками проверяет актуальное состояние и одобрение. Создаёт выдачу и меняет статус вместе. UNIQUE по item_id дополнительно запрещает дубль.

**Проверка.** Через разные соединения с согласованным стартом отправляются два допустимых запроса. Без искусственных сбоев успешен один. В базе одна выдача с правильным получателем, вещь выдана. Затем проверяется повтор запроса.

Блокировка не удерживается во время разговора с заявителем: сотрудник проверяет принадлежность заранее, а транзакция оформляет уже принятое решение.

## Текст выступления M3

Моя часть проекта — компоненты, минимальное ядро и стек, а также безопасность выдачи найденной вещи.

В итоговой версии клиент обращается к REST API, сервер проверяет данные и права, выполняет операции и сохраняет результат в PostgreSQL. Все значимые проверки находятся на сервере, потому что запрос можно изменить или отправить напрямую. CLI, фотографии и облачное размещение можно отложить. Сейчас работает основа на FastAPI и Uvicorn с маршрутом /health; база и предметные операции пока проектируются.

В блоке выдачи выделены три угрозы: неподходящая заявка или подмена получателя, повторная выдача при одновременных запросах и частичное сохранение при сбое.

Первое требование разрешает выдачу только ответственному сотруднику по одобренной заявке на эту вещь. Получатель берётся из сохранённой заявки. Второе запрещает повторную выдачу, в том числе при конкуренции. Третье требует сохранять выдачу и статус вещи вместе.

Предложено решение с транзакцией PostgreSQL. Сервер блокирует строку вещи, затем заявки, проверяет актуальные данные, создаёт выдачу и меняет статус одной транзакцией. Уникальность идентификатора вещи дополнительно запрещает вторую запись.

Основная цепочка моего блока — повторная выдача, требование единственности, блокировка и ограничение уникальности, затем проверка двумя одновременными запросами. В работающей системе без искусственных сбоев должен завершиться один запрос, а в базе остаться одна выдача.

Пока это проектное решение и план проверок. Оно защищает учёт, но не заменяет проверку владельца и не исключает ошибку сотрудника при физической передаче вещи.

## Вопросы по выдаче

**Что ограничивают требования и как это влияет на безопасность?** SR-ISS-01 ограничивает роль и основание выдачи; это защищает от неподтверждённой выдачи и подмены получателя. SR-ISS-02 ограничивает количество записей; это предотвращает противоречивые сведения о возврате. SR-ISS-03 запрещает частичное сохранение связанных результатов.

**Почему недостаточно проверки состояния?** Два запроса могут прочитать одно старое состояние до его изменения. Нужна координация проверки и записи.

**Зачем транзакция, блокировка и UNIQUE?** Транзакция сохраняет связанные изменения вместе. Блокировка позволяет проверить актуальное состояние при конкуренции. UNIQUE запрещает две записи одной вещи. Одна транзакция с обычным чтением не исключает гонку автоматически.

**Что происходит со вторым запросом?** При попытке заблокировать ту же вещь он ждёт. После commit первого видит «выдана» и получает отказ. После rollback первого может выполнить выдачу.

**Почему не mutex в Python?** Он действует внутри одного процесса. PostgreSQL координирует процессы сервера, которые работают с общей базой.

**Что такое атомарность?** Связанные изменения фиксируются целиком или не фиксируются. Не остаётся выдачи без нового статуса либо статуса «выдана» без сведений о выдаче.

**Что если ответ потерялся?** Потеря ответа после commit не отменяет выдачу. При потере связи во время commit исход может быть неизвестен. Нужно прочитать состояние; повтор не создаёт вторую запись.

**Зачем блокировать заявку?** Чтобы её состояние и основание не изменились между проверкой и сохранением выдачи. После выдачи обычные операции также не должны менять вещь, получателя или решение в этой заявке.

**Что проверяют внешние ключи?** Существование связанных записей. Они сами по себе не подтверждают одобрение заявки и соответствие нужной вещи; это проверяет сервер.

**Можно ли иметь две одобренные заявки?** Паспорт пока этого не запрещает. Проверка конкуренции использует такой случай, но две одобренные заявки не дают право на две выдачи.

**Где граница решения?** Оно защищает записи одной системы с одной PostgreSQL и одним циклом хранения. Для повторного приёма вещи потребуется модель циклов. Решение не предотвращает ложь заявителя и физическую передачу не той вещи.

**Проверки уже выполнены?** Запуск API, его тест и проверки Ruff выполнены. CHECK-ISS пока планы: выдачи и базы в коде нет.

## Доступ и другие риски

По D-ACCESS-01 сервер проверяет токен, роль, автора заявки и разрешённые поля. Действующий токен не разрешает читать чужие заявки. Скрытые признаки не возвращаются пользователю или гостю, включая вложенную карточку вещи.

Аутентификация устанавливает пользователя, авторизация определяет разрешённые действия. Роль берётся из базы; поле role в запросе не даёт полномочий.

Планируется случайный токен, в базе — его SHA-256, пользователь и срок действия. Пароли хешируются Argon2id. Токен действует 48 часов без продления запросами и может быть отозван. В сети используется HTTPS; необязательный CLI хранит исходный токен в системном хранилище.

Риски существуют и вне базы: кража аккаунта или токена, неверные проверки прав в API, утечка скрытых признаков и секретов через ответы или логи, ошибки сотрудника. Транзакции не закрывают эти риски.

## Понятия для индивидуального вопроса

- Конфиденциальность — закрытые сведения не получает посторонний. Целостность — данные и состояние не меняются недопустимым образом. Доступность — разрешённые операции можно выполнить.
- Угроза — возможный сценарий нарушения. Уязвимость — слабость, позволяющая ему произойти. Ошибка или сбой тоже могут создавать угрозу.
- Граница доверия — место, где нельзя полагаться на данные другой стороны. В Locate это клиент → API; вход пользователя не делает его поля достоверными.
- Минимальные привилегии — роль получает только нужные полномочия. Полное посредничество — проверки действуют для всех путей к данным, включая списки и вложенные объекты.
- Разделение обязанностей — регистрация и выдача относятся к разным ролям. Само наличие двух ролей ещё не доказывает проверку двумя разными людьми.
- Артефакт — код, документ или тест. Свидетельство — проверяемое подтверждение конкретного свойства; успешный /health не доказывает безопасность выдачи.
