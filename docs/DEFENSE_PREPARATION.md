# Подготовка к защите Locate

Locate — REST API бюро находок. Сотрудник регистрирует вещь, пользователь заявляет о принадлежности, ответственный сотрудник проверяет заявку и оформляет выдачу. На EK1 защищаем концепцию безопасности и минимальную серверную основу. Сейчас в коде работает только маршрут `/health`; каталог, заявки, авторизация и PostgreSQL описаны как следующие этапы.

Разбор относится к `main` на коммите `5b8255d83ba94e8797e91eab2b22030ef49c0732`, просмотренном 6 октября. Это просмотренная версия, а не подтверждение передачи её преподавателю. По переписке слот команды — 6 октября, 16:30–16:40. Точный срок предварительной сдачи и переданный hash нужно проверить у команды.

## Продукт и роли

**Регистрация находки:** вещь принесли в бюро; сотрудник записывает открытое описание, скрытые признаки, место и время. Вещь становится доступной для поиска и остаётся на хранении.

**Поиск и заявка:** посетитель смотрит открытый каталог. Для подачи заявки входит в систему, указывает сведения о себе и признаки вещи, подтверждающие владение. Вещь ещё не выдана.

**Рассмотрение и возврат:** ответственный сотрудник сравнивает сведения заявителя со скрытыми признаками. Одобряет или отклоняет заявку. После одобрения отдельно оформляет выдачу с получателем, сотрудником и временем. Одобрение и выдача — разные события.

| Роль | Основные права | Основные ограничения |
| --- | --- | --- |
| Гость | Открытый каталог | Не подаёт и не читает заявки, не получает скрытые признаки |
| Пользователь | Подаёт заявку, читает свои, меняет свои сведения до решения | Не читает чужие заявки, не назначает себе роль, не выдаёт вещи |
| Сотрудник регистрации | Создаёт и редактирует карточки вещей, вводит скрытые признаки | Не рассматривает заявки и не оформляет выдачу |
| Ответственный сотрудник | Читает заявки и скрытые признаки, принимает решение, выдаёт вещь | Не меняет карточки вещей и сведения, написанные заявителем |

Отдельное право чтения скрытых признаков сотрудником регистрации ещё требует уточнения: паспорт разрешает ему ввод и редактирование, а блок Егора не определяет его чтение. Также команда пока не согласовала редактирование заявки после решения. Наше решение предлагает запрет изменения связи с вещью и получателем после выдачи.

Значимые данные: персональные сведения заявителя, доказательства владения, скрытые признаки, решение и запись о выдаче. Утечка признаков помогает притвориться владельцем; подмена решения или несогласованные записи могут привести к неправомерной выдаче.

## Как устроен код

Путь запроса: клиент → Uvicorn → FastAPI → маршрут `/health` → `HealthResponse` → JSON-ответ клиенту.

| Файл | Что делает |
| --- | --- |
| `src/locate/__init__.py` | Задаёт версию пакета |
| `src/locate/bootstrap.py` | `create_app()` создаёт FastAPI-приложение, задаёт название и версию, подключает router |
| `src/locate/presentation/api/routes.py` | `APIRouter` содержит маршрут `GET /health`; обработчик возвращает `HealthResponse()` |
| `src/locate/presentation/api/schemas.py` | `HealthStatus.OK` имеет значение `ok`; Pydantic-модель задаёт поле `status` с этим значением по умолчанию |
| `tests/api/test_health.py` | Через TestClient собирает приложение и проверяет HTTP 200, Content-Type и точный JSON |
| `pyproject.toml` | Метаданные пакета, Python ≥3.12, прямые зависимости, инструменты разработки |
| `requirements.lock` | Фиксирует версии прямых и транзитивных зависимостей; используется как constraints при установке |

`--factory` означает, что Uvicorn вызывает функцию `create_app`, чтобы получить приложение. FastAPI задаёт маршруты, Uvicorn принимает HTTP-запросы как ASGI-сервер, Pydantic описывает структуру ответа. У FastAPI есть автоматическая документация `/docs`; это служебный интерфейс API, а не пользовательский сайт бюро находок. [Документация FastAPI](https://fastapi.tiangolo.com/tutorial/first-steps/).

`/health` всегда возвращает `{"status":"ok"}`. Он не обращается к базе и не проверяет авторизацию. Это простой признак работы HTTP-основы, а не проверка готовности всего будущего продукта.

TestClient выполняет запрос внутри тестового процесса. Такой тест проверяет сборку и HTTP-контракт приложения, но не подтверждает, что Uvicorn реально слушает порт. Для этого нужен отдельный запуск и запрос `curl`.

## Запуск и демонстрация

Команды из README для macOS/Linux, из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -c requirements.lock -e ".[dev]"
python -m uvicorn locate.bootstrap:create_app --factory --host 127.0.0.1 --port 8000
```

В другом терминале:

```bash
curl -i http://127.0.0.1:8000/health
```

Ожидаются HTTP 200, `content-type: application/json` и `{"status":"ok"}`. Адрес `127.0.0.1` означает доступ только с этого компьютера. В браузере можно открыть `http://127.0.0.1:8000/docs`. Остановка сервера — Ctrl+C.

Для проверки версии нужны `git rev-parse HEAD` и `git status --short`. На защите демонстрируется та версия, которая была передана преподавателю, а не автоматически самый свежий коммит.

В PR №4 Егор сообщил об успешной установке, `pip check`, одном тесте pytest, проверках Ruff и реальном запросе к Uvicorn. 6 октября основа повторно проверена в отдельном окружении: pip check, pytest и Ruff прошли, реальный GET /health вернул 200. ## Что означают SR T и D

- **T — угроза:** конкретный способ нарушить безопасность и его последствия. Например, два запроса фиксируют выдачу одной вещи.
- **SR — требование:** какое защитное свойство обязана обеспечить система. Например, у вещи не больше одной выдачи. Критерий приёмки задаёт наблюдаемый результат.
- **D — решение:** выбранный механизм и его обоснование. Например, транзакция, блокировка строки и ограничение уникальности.
- **Будущая проверка:** на каких данных и какими действиями проверим механизм. План становится свидетельством только после выполнения и фиксации результата для конкретной версии.

Простой пример цепочки: два сотрудника одновременно нажали выдачу → система обязана сохранить только одну выдачу → сервер блокирует вещь в транзакции → отправим два параллельных запроса и проверим ответы и записи в базе.

## Твоя часть о выдаче

**SR-04:** выдача только по одобренной заявке на эту вещь. Сервер берёт получателя из заявки, а не доверяет произвольному параметру клиента.

**SR-05:** одна вещь — максимум одна выдача, включая повтор и параллельные запросы.

**SR-06:** запись о выдаче и статус вещи сохраняются вместе. Если операция прервалась до фиксации, частичных изменений быть не должно.

Первые две угрозы имеют высокий приоритет: один неправильный запрос или обычные параллельные действия могут привести к неправомерной выдаче. Сбой посередине операции имеет средний приоритет, но также покрывается решением.

Механизм D-02:

1. Определить личность и проверить роль ответственного сотрудника по решению Егора.
2. Начать транзакцию, заблокировать строку вещи через `SELECT ... FOR UPDATE`, затем строку заявки.
3. Под блокировкой проверить состояние вещи, одобрение и связь заявки с этой вещью.
4. Создать запись о выдаче, изменить состояние вещи и зафиксировать оба изменения.
5. Ограничение `UNIQUE(item_id)` дополнительно запрещает вторую запись о выдаче этой вещи.

**Транзакция** объединяет изменения по правилу «всё или ничего». **Блокировка** координирует конкурирующие операции с одной вещью. **Уникальность** запрещает дубли в базе. Эти механизмы решают разные части задачи. Поведение соответствует описанию [транзакций](https://www.postgresql.org/docs/current/tutorial-transactions.html) и [блокировок строк PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS).

Планируем Read Committed. Если первая операция успешно выдала вещь, второй запрос после ожидания увидит обновлённое состояние и откажется от выдачи. Если первая откатилась, второй может выдать вещь. Обычное чтение строки само по себе не блокируется `FOR UPDATE`; координируются изменения и запросы на блокировку той же строки.

Проверки: неподходящие заявки отклоняются без изменений; из двух допустимых одновременных выдач успешна одна; искусственная ошибка до commit отменяет и запись, и изменение статуса. Для конкуренции нужны отдельные соединения и согласованный старт, а не два последовательных запроса.

## Короткое объяснение твоей цепочки

«Я взял целостность выдачи. Если два сотрудника одновременно оформляют одну вещь, оба запроса могут прочитать старое состояние “на хранении”. Одной проверки состояния недостаточно: система может подтвердить две выдачи.

Требование — не больше одной выдачи на вещь, в том числе при параллельных запросах. Критерий: ровно один запрос успешен, в базе одна запись и один получатель.

Для будущей реализации выбрали транзакцию PostgreSQL с блокировкой строки вещи. После получения блокировки проверяем состояние и одобренную заявку, создаём выдачу и меняем статус вместе. Второй запрос ждёт, затем проверяет актуальное состояние. Ограничение уникальности дополнительно запрещает дубль.

Проверим это двумя запросами через отдельные соединения и проверкой базы. Сейчас выдача не реализована, поэтому это план проверки. Текущая техническая основа — работающий HTTP-сервер с `/health`».

## Блок Егора о доступе

Три угрозы: чтение чужой заявки, изменение чужой заявки и раскрытие скрытых признаков. Защита должна проверять роль, автора объекта и разрешённые поля на сервере. Скрыть кнопку в клиенте недостаточно: пользователь может отправить запрос напрямую.

Аутентификация отвечает на вопрос «кто обращается», авторизация — «что этому пользователю разрешено». Действующий токен подтверждает личность, но не даёт доступ к любой заявке.

В проектном решении используется случайный непрозрачный токен, а не JWT. Сервер генерирует его через `secrets.token_urlsafe(32)`, сохраняет SHA-256 токена, пользователя и даты. Клиент передаёт исходный токен в `Authorization: Bearer ...`. Сервер вычисляет хеш и ищет запись. Пароли планируется хранить через Argon2id с отдельной солью; SHA-256 не выбран для паролей.

Токен действует 48 часов без продления запросами. При отзыве удаляется запись именно этого токена. После подтверждённого отзыва новые запросы отклоняются; уже прошедший проверку запрос может завершиться. В CLI токен планируется хранить в системном keyring. Все эти механизмы пока описаны в документации, а не реализованы.

## Вопросы преподавателя и смысл ответа

**Почему это безопасность, а не только бизнес-логика?** Неправомерная выдача затрагивает имущество, а подмена решения и противоречивые сведения нарушают целостность учёта. Требования защищают значимые данные и основание передачи вещи.

**Почему не достаточно проверить статус перед выдачей?** Между чтением и записью другой запрос может сделать то же самое. Проверка должна быть связана с изменением в защищённой транзакции.

**Почему одной транзакции мало?** Атомарность не гарантирует нужного порядка конкурирующих проверок при выбранном уровне изоляции. Нужны блокировка или другой конкретный механизм конкуренции и ограничение уникальности.

**Почему не mutex в Python?** Он действует только внутри одного процесса. Несколько процессов или экземпляров сервера должны координироваться через общую базу.

**Зачем блокировать заявку?** Чтобы решение, связь с вещью и получатель не изменились между проверкой и фиксацией выдачи.

**Что такое deadlock?** Две операции ждут ресурсы, занятые друг другом. Одинаковый порядок блокировок уменьшает риск; ошибка должна завершать транзакцию без частичного результата.

**Что будет, если сервер упадёт после commit, но до ответа?** Выдача уже сохранена. Повторный запрос не создаст новую; сотрудник должен прочитать результат. Потеря ответа не означает отмену зафиксированной операции.

**Почему не реализовали все функции?** EK1 требует минимальный запускаемый сервер и связанную концепцию безопасности. Полная реализация сценариев и все технические проверки решений на этом этапе не обязательны. Источник — [правила EK1](https://github.com/Ksiren/Locate-software/blob/5b8255d83ba94e8797e91eab2b22030ef49c0732/useful%20files/EK1.md).

**Что доказывает health?** Что приложение обработало HTTP-запрос и вернуло ожидаемый ответ. Он не доказывает защиту данных, работу базы и сценариев.

**Что такое Clean Architecture в вашем коде?** Разделение бизнес-правил, сценариев и внешних адаптеров с зависимостями внутрь. Пока есть только сборка и HTTP-слой. Domain не должен зависеть от FastAPI или SQLAlchemy; конкретные зависимости связывает bootstrap.

**Почему нельзя доверять роли в запросе?** Пользователь может её подменить. Сервер получает роль из доверенного хранения по установленной личности.

**Чем 401 отличается от отказа из-за прав?** 401 означает отсутствие допустимой аутентификации. Установленная личность тоже может не иметь права на операцию; конкретные коды отказов для предметных операций ещё нужно зафиксировать.

**Почему токен — не пароль?** Пароль используется при входе; далее клиент предъявляет отдельный случайный секрет с ограниченным сроком и возможностью отзыва.

**Почему HTTPS, если пароль в JSON?** JSON-тело не шифрует передачу. HTTPS защищает транспорт. Текущий локальный `/health` не принимает секреты и демонстрируется по HTTP на loopback; это не конфигурация будущего публичного сервиса.

**Зачем хеш токена?** База не хранит готовый секрет, который можно сразу предъявить API. Это не заменяет защиту доступа к базе и логам.

**Почему 48 часов?** Это выбранный командой компромисс удобства и времени действия украденного токена, а не универсальный безопасный срок. Для чувствительных ролей выбор можно пересмотреть.

**Что ваше решение не защищает?** От прямого доступа к базе, кражи аккаунта, ложных доказательств и ошибки при физической передаче. У блоков разные допущения и границы.

**Можно ли выдать вещь повторно после нового приёма?** Текущая модель предполагает один цикл хранения. Для повторного приёма нужна новая модель циклов и пересмотр уникальности.

**Какие тесты уже есть?** В репозитории один тест `/health`. Проверки доступа и выдачи ещё планы. При описании результатов нужно назвать, кто и на какой версии выполнил проверку.

**Какой твой вклад?** Подготовлены пункты 6, 8 и 9 паспорта, отправленные в PR №3. В этой редакции добавлен блок целостности выдачи: три SR, три угрозы, одно решение и планы проверок. Серверную основу подготовил Егор; повторная автоматическая проверка запуска описана в LOCAL_VALIDATION.md.

Для команды: около 45 секунд на назначение, сценарии и границу доверия; до двух минут на одну цепочку; затем подтверждение запуска и индивидуальные вопросы. Отдельная презентация не требуется.

Сначала без подсказок объясни: чем одобрение отличается от выдачи; почему два запроса опасны; зачем нужны и транзакция, и блокировка, и UNIQUE; что уже есть в коде. Затем попробуй ответить: «А если первый запрос откатился?», «А если commit прошёл, но ответ потерялся?», «А если пользователь подменил роль?». Уверенное объяснение этих случаев полезнее заучивания названий библиотек.

## Понятия из лекций для индивидуального вопроса

**L01 — контекст и смысл подтверждения.** Актив — данные, функция, ресурс или состояние, нарушение защиты которых причинит значимый ущерб. В Locate это персональные сведения, скрытые признаки, решение и достоверный учёт выдачи. Конфиденциальность ограничивает раскрытие, целостность защищает от недопустимых изменений, доступность обеспечивает своевременную работу для уполномоченных пользователей.

Граница продукта показывает, за какие части отвечает команда. Граница доверия показывает, где меняются основания доверять данным или полномочиям. Они не обязаны совпадать: собственный CLI тоже отправляет недоверенный ввод серверу.

Артефакт — сохранённый результат: документ, код, тест, коммит. Свидетельство — фактически полученный результат с известной версией, способом получения и обоснованной интерпретацией. Один успешный `/health` подтверждает только этот контракт, а не безопасность всех будущих операций.

Цикл курса: контекст и активы → требование или угроза → решение → изменение продукта → проверка → при необходимости исправление и повторная проверка → решение о выпуске. SSDF — профессиональная рамка практик безопасной разработки; коды всех практик заучивать не требуется. [Лекция L01](https://github.com/hse-rbpo-bachelor-2026/course/blob/main/lectures/L01.pdf).

**L02 — формулировка требования.** «Использовать транзакцию» — мера, а «не допускать повторной выдачи» — требуемое свойство. Безопасность бизнес-правила нужно обосновать последствиями: в нашем случае нарушение создаёт ложные сведения об основании выдачи и получателе и может привести к неправомерной передаче вещи.

Критерий приёмки описывает ситуацию и ожидаемый результат. Будущая проверка задаёт действия, чтобы его наблюдать. Фактический результат появляется после выполнения. Нужны и отказ в запрещённом случае, и успешная полезная операция: сервер, который запрещает вообще всё, не выполняет назначение продукта.

ASVS — каталог требований OWASP, который помогает находить и уточнять применимые свойства. Он не заменяет анализ своего продукта. Курс использует ASVS 5.0.0, конкретная ссылка должна включать версию и ID; не нужно придумывать номер пункта, если он не проверен. [Лекция L02](https://github.com/hse-rbpo-bachelor-2026/course/blob/main/lectures/L02.pdf).

**L03 — модель угроз.** Это модель значимых компонентов, потоков и границ плюс конкретные угрозы, приоритеты и связи с SR. DFD показывает внешних субъектов, процессы, хранилища и потоки данных. Подпись потока «данные заявки» полезнее подписи «HTTPS»: она показывает, что именно можно подменить или раскрыть.

Угроза — возможный сценарий нарушения, уязвимость — слабость, которая позволяет его осуществить. При моделировании будущего продукта угрозу можно описать до появления кода. Сбой или ошибка сотрудника также могут быть угрозой; злой умысел не обязателен.

STRIDE — вопросник по подмене идентичности, изменению, отрицанию действий, раскрытию, отказу в обслуживании и повышению привилегий. Не нужно искусственно создавать шесть угроз. Приоритет объясняется предпосылками и тяжестью последствий. Редкий сбой не становится автоматически незначительным. [Лекция L03](https://github.com/hse-rbpo-bachelor-2026/course/blob/main/lectures/L03.pdf).

**L04 — обоснование решения.** D объясняет конкретный механизм, место применения, доверенные данные, причины выбора, предположения, ограничения и проверку. Предположение — условие, на котором держится решение: например, все выдачи проходят через одну базу. Ограничение — то, чего оно не обещает: транзакция не предотвращает физическую передачу не той вещи.

Пять принципов и применение к Locate:

- Минимальные привилегии: пользователь работает со своими заявками, роли сотрудников ограничены нужными действиями.
- Безопасные значения по умолчанию: без установленного разрешения защищённая операция не выполняется; ошибка проверки не превращается в разрешение.
- Полное посредничество: права проверяются для каждого пути к данным, включая списки, поиск и вложенные объекты.
- Разделение обязанностей: регистрация находки и оформление выдачи относятся к разным ролям. Но это ещё не доказательство контроля двумя людьми: паспорт не запрещает совмещать роли одному человеку.
- Минимизация поверхности воздействия: обязательному продукту не нужны лишние интерфейсы и интеграции; CLI и облако можно отложить.

[Лекция L04](https://github.com/hse-rbpo-bachelor-2026/course/blob/main/lectures/L04.pdf).

## Как оценивать готовность к 8 и к 9–10

База: требования — 2, угрозы — 2, согласованность — 2, решения — 1, наблюдаемость — 1. Всего 8 при полной базе. Недостаток запуска или своевременно зафиксированной версии обнуляет наблюдаемость для команды; личный неподтверждённый вклад рассматривается отдельно для участника.

Повышенная согласованность требует своего нетривиального контрпримера, который меняет первоначально правдоподобную цепочку и будущую проверку. Повышенный уровень решения требует сравнить два применимых способа, показать компромисс, условия выбора и пересмотра, соответствующую проверку. Mutex в одном процессе не является полноценной применимой альтернативой для сервера с несколькими процессами; объяснение, почему он не подходит, само по себе не гарантирует повышенный уровень.

Наш блок хорошо подходит для базовой защиты. Обычная гонка «проверил, потом записал» близка к учебному кейсу S04 и не гарантирует балл за собственный нетривиальный контрпример. Также текущий текст не даёт оснований обещать 9–10: важны полный командный комплект, сданная версия и личное объяснение. [Рубрика EK1](https://github.com/hse-rbpo-bachelor-2026/course/blob/main/assessment/EK1.md).

## Уточнения после локальной проверки 6 октября

Основу действительно запустили в отдельном окружении: /health отвечает 200, единственный тест проходит, Ruff и pip check успешны. Окружение и временная копия удалены. Это демонстрация запуска, а проверки выдачи остаются планом.

В твоём SR-04 право выдачи есть у ответственного сотрудника. Сервер берёт получателя из сохранённой одобренной заявки на эту же вещь; произвольное поле recipient_id от клиента не определяет получателя.

В D-02 сначала блокируем строку вещи в PostgreSQL, потом проверяем состояние и заявку. В одной транзакции создаём выдачу и меняем статус вещи. UNIQUE по item_id страхует единственность записи. После выдачи обычные операции не должны позволять заменить вещь, получателя или решение в связанной заявке.

Если ошибка подтверждённо произошла до commit, изменения откатываются. Если связь потеряна во время commit, результат неизвестен: сначала читаем состояние. Потеря ответа после успешного commit не отменяет выдачу. Повторный запрос не должен создавать вторую запись.

Фраза для защиты: «Я отвечаю за целостность выдачи. Мы пока описали требования и проект решения, а в коде сделали минимальную запускаемую основу. Для выдачи нужно проверить роль, одобренную заявку на нужную вещь, исключить повторную запись и сохранить выдачу со статусом одной транзакцией. Это будем проверять обычными запросами, двумя одновременными запросами через разные соединения и искусственным сбоем перед commit».
