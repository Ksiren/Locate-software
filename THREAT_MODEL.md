# Модель угроз

## Граница рассматриваемого блока

Блок описывает доступ к заявкам и скрытым признакам вещей из [паспорта проекта](PROJECT.md). Чтение рассматривается для любого состояния заявки, изменение сведений заявителя - до решения. Подробная модель угроз регистрации, входа и хранения токенов, решения по заявкам и выдача вещей рассматриваются отдельно.

Путь данных: CLI или другой HTTP-клиент -> REST API -> PostgreSQL. Для входа используем токен нашего сервиса. Клиент передаёт его в заголовке `Authorization: Bearer <token>`. В запросе также могут быть идентификаторы объектов, фильтры и новые значения полей. API проверяет токен и права, затем читает или изменяет записи. Реализация и проверки пока не выполнены.

**Значимые данные:** сведения заявителя, подтверждение владения и скрытые признаки вещи. Утечка помогает выдать чужую вещь за свою. Подмена данных может повлиять на решение сотрудника и помешать возврату владельцу.

**Граница доверия:** клиент -> API. Пользователь может изменить запрос или отправить его без CLI. Даже действующий токен не даёт доступа к чужой заявке. Сервер отдельно проверяет права на объект; роль и автор из запроса не дают дополнительных прав.

**Допущения и открытые вопросы:**

- Сервер находит токен в БД по SHA-256 и проверяет срок действия: 48 часов с момента выдачи, без продления запросами. По записи токена определяет пользователя, его роль также получает из БД. План регистрации и проверки пароля описан в [решении](SECURITY_DECISIONS.md#регистрация-и-вход), генерация токена и досрочный отзыв через `POST /auth/revoke` - в [схеме токена](SECURITY_DECISIONS.md#токен-и-отзыв), хранение на клиенте - в [схеме CLI](SECURITY_DECISIONS.md#вход-через-cli). Политика паролей, параметры Argon2id и защита от перебора требуют отдельного решения.
- PostgreSQL доступен только серверу. Это нужно обеспечить при развёртывании.
- Можно ли менять заявку после решения, ещё не определено.
- По паспорту сотрудник регистрации вводит и меняет скрытые признаки. Его отдельное право чтения нужно уточнить; этот блок его не определяет.

## T-ACCESS-01

**Чтение чужой заявки.** Пользователь меняет идентификатор заявки или фильтр списка. Если API не проверяет автора, пользователь получает чужие сведения и подтверждение владения. Нарушается конфиденциальность.

- Точки входа: чтение заявки, список и поиск заявок через API.
- Приоритет: высокий, входит в приоритетный набор. Достаточно обычного HTTP-запроса. Утечка может затронуть нескольких заявителей и дать сведения для ложной заявки.
- Связи: [SR-ACCESS-01](SECURITY_REQUIREMENTS.md#sr-access-01), [D-ACCESS-01](SECURITY_DECISIONS.md#d-access-01), [будущая проверка 1](SECURITY_DECISIONS.md#проверка-1).

## T-ACCESS-02

**Изменение чужой заявки.** Пользователь подставляет в запрос изменения идентификатор чужой заявки, которая ожидает рассмотрения. Если API не проверяет автора, сервер сохраняет правки. Это может повлиять на решение сотрудника или сорвать возврат владельцу. Нарушается целостность.

- Точка входа: изменение сведений заявителя и подтверждения принадлежности через API.
- Приоритет: высокий, входит в приоритетный набор. Атакующий использует обычную операцию редактирования и меняет сведения, по которым сотрудник принимает решение.
- Связи: [SR-ACCESS-02](SECURITY_REQUIREMENTS.md#sr-access-02), [D-ACCESS-01](SECURITY_DECISIONS.md#d-access-01), [будущая проверка 2](SECURITY_DECISIONS.md#проверка-2).

## T-ACCESS-03

**Раскрытие скрытых признаков вещи.** Пользователь запрашивает карточку, каталог или свою заявку. Если сервер возвращает полную запись вещи, в ответ попадают скрытые признаки. Их можно указать в ложной заявке как доказательство владения. Нарушается конфиденциальность.

- Точки входа: каталог, карточка вещи и вложенная карточка в ответе по заявке.
- Приоритет: высокий, входит в приоритетный набор. Достаточно посмотреть ответ API. Получив скрытые признаки, заявитель может обмануть сотрудника при проверке владельца.
- Связи: [SR-ACCESS-03](SECURITY_REQUIREMENTS.md#sr-access-03), [D-ACCESS-01](SECURITY_DECISIONS.md#d-access-01), [будущая проверка 3](SECURITY_DECISIONS.md#проверка-3).

Все три угрозы связаны с границей клиент -> API. Это возможные ошибки будущего кода. Приоритеты пока предварительные: они учитывают последствия и простоту запросов через API. Их нужно сверить с остальными угрозами проекта.
