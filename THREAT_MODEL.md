# Модель угроз

## Граница рассматриваемого блока

Модель описывает доступ к заявкам и скрытым признакам вещей, а также оформление выдачи из [паспорта проекта](PROJECT.md). Чтение заявок рассматривается для любого состояния, изменение сведений заявителя — до решения. Регистрация, вход и хранение токенов описаны как условия контроля доступа; их подробная модель угроз рассматривается отдельно.

Путь данных: CLI или другой HTTP-клиент -> REST API -> PostgreSQL. Для входа используем токен нашего сервиса. Клиент передаёт его в заголовке `Authorization: Bearer <token>`. Клиент передаёт идентификаторы вещей и заявок, фильтры и новые значения полей. API проверяет токен и права, затем читает или изменяет записи. При выдаче сохраняет получателя и состояние вещи. Реализация этих операций и проверки пока не выполнены.

**Значимые данные:** сведения заявителя, подтверждение владения, скрытые признаки вещи, решение по заявке, состояние вещи и запись о выдаче. Утечка признаков помогает выдать чужую вещь за свою. Подмена или несогласованное сохранение данных могут повлиять на возврат владельцу и достоверность учёта.

**Граница доверия:** клиент → API. Пользователь или сотрудник может изменить запрос или отправить его без CLI. Даже действующий токен не даёт дополнительных прав. Сервер проверяет действие и объект; роль получает из БД, автора и получателя — из сохранённой заявки.

**Допущения и открытые вопросы:**

- Сервер находит токен в БД по SHA-256 и проверяет срок действия: 48 часов с момента выдачи, без продления запросами. По записи токена определяет пользователя, его роль также получает из БД. План регистрации и проверки пароля описан в [решении](SECURITY_DECISIONS.md#регистрация-и-вход), генерация токена и досрочный отзыв через `POST /auth/revoke` - в [схеме токена](SECURITY_DECISIONS.md#токен-и-отзыв), хранение на клиенте - в [схеме CLI](SECURITY_DECISIONS.md#вход-через-cli). Политика паролей, параметры Argon2id и защита от перебора требуют отдельного решения.
- PostgreSQL доступен только серверу. Это нужно обеспечить при развёртывании.
- Можно ли менять сведения заявки после решения, ещё не определено. После выдачи D-ISS-01 запрещает обычным операциям менять её основание: вещь, получателя и решение.
- Все выдачи проходят через сервер и одну PostgreSQL. Модель предполагает один цикл хранения вещи.
- Для проверки конкуренции допускаем две одобренные заявки на одну вещь: паспорт не запрещает это. Одобрение заявки само по себе не означает выдачу.
- По паспорту сотрудник регистрации вводит и меняет скрытые признаки. Его отдельное право чтения нужно уточнить; этот блок его не определяет.

## T-ACCESS-01

**Чтение чужой заявки.** Пользователь меняет идентификатор заявки или фильтр списка. Если API не проверяет автора, пользователь получает чужие сведения и подтверждение владения. Нарушается конфиденциальность.

- Точки входа: чтение заявки, список и поиск заявок через API.
- Приоритет: высокий, входит в приоритетный набор. Достаточно обычного HTTP-запроса. Утечка может затронуть нескольких заявителей и дать сведения для ложной заявки.
- Связи: [SR-ACCESS-01](SECURITY_REQUIREMENTS.md#sr-access-01), [D-ACCESS-01](SECURITY_DECISIONS.md#d-access-01), [будущая проверка 1](SECURITY_DECISIONS.md#проверка-1).

## T-ACCESS-02

**Изменение чужой заявки.** Пользователь подставляет в запрос изменения идентификатор чужой заявки, которая ожидает рассмотрения. Если API не проверяет автора, сервер сохраняет правки. Это может повлиять на решение сотрудника или сорвать возврат владельцу. Нарушается целостность.

- Точка входа: изменение сведений заявителя и подтверждения принадлежности через API.
- Приоритет: высокий, входит в приоритетный набор. Атакующий использует обычную операцию редактирования и меняет сведения, по которым сотрудник принимает решение.
- Связи: [SR-ACCESS-02](SECURITY_REQUIREMENTS.md#sr-access-02), [D-ACCESS-01](SECURITY_DECISIONS.md#d-access-01), [будущая проверка 2](SECURITY_DECISIONS.md#проверка-2).

## T-ACCESS-03

**Раскрытие скрытых признаков вещи.** Пользователь запрашивает карточку, каталог или свою заявку. Если сервер возвращает полную запись вещи, в ответ попадают скрытые признаки. Их можно указать в ложной заявке как доказательство владения. Нарушается конфиденциальность.

- Точки входа: каталог, карточка вещи и вложенная карточка в ответе по заявке.
- Приоритет: высокий, входит в приоритетный набор. Достаточно посмотреть ответ API. Получив скрытые признаки, заявитель может обмануть сотрудника при проверке владельца.
- Связи: [SR-ACCESS-03](SECURITY_REQUIREMENTS.md#sr-access-03), [D-ACCESS-01](SECURITY_DECISIONS.md#d-access-01), [будущая проверка 3](SECURITY_DECISIONS.md#проверка-3).

## T-ISS-01

**Неподходящая заявка или подмена получателя.** Сотрудник по ошибке либо намеренно передаёт ID отклонённой заявки, заявки на другую вещь или другого получателя. Если API доверяет этим полям без проверки сохранённой заявки, выдача оказывается связана с неподтверждённым решением. Нарушается целостность основания выдачи; вещь может получить не тот человек.

- Точка входа: будущая операция оформления выдачи через API.
- Приоритет: высокий, входит в приоритетный набор. Достаточно одного запроса, последствия затрагивают возврат реальной вещи владельцу.
- Связи: [SR-ISS-01](SECURITY_REQUIREMENTS.md#sr-iss-01), [D-ISS-01](SECURITY_DECISIONS.md#d-iss-01), [CHECK-ISS-01](SECURITY_DECISIONS.md#check-iss-01).

## T-ISS-02

**Повторная выдача при конкурирующих запросах.** Два сотрудника одновременно оформляют одну вещь, либо клиент повторяет запрос. Если каждый запрос отдельно читает состояние «на хранении», а затем записывает выдачу без защиты от конкуренции, оба могут завершиться успешно. Система подтверждает две выдачи одной вещи и сохраняет противоречивые сведения о получателе.

- Точка входа: повторные или одновременные запросы оформления выдачи.
- Приоритет: высокий, входит в приоритетный набор. Параллельная обработка предусмотрена архитектурой; ошибка возможна при обычной работе.
- Связи: [SR-ISS-02](SECURITY_REQUIREMENTS.md#sr-iss-02), [D-ISS-01](SECURITY_DECISIONS.md#d-iss-01), [CHECK-ISS-02](SECURITY_DECISIONS.md#check-iss-02).

## T-ISS-03

**Частично сохранённая выдача после сбоя.** Запись о выдаче и состояние вещи сохраняются независимо. Между действиями возникает ошибка. Вещь остаётся доступной при уже сохранённой выдаче либо считается выданной без получателя. Нарушается целостность учёта; появляется возможность повторной выдачи или теряются сведения о возврате.

- Точка возникновения: работа сервера с базой при оформлении выдачи.
- Приоритет: средний. Требуется сбой между связанными изменениями; первые две угрозы достижимы обычными запросами. Последствия значимы; угроза покрывается тем же решением и отдельной проверкой.
- Связи: [SR-ISS-03](SECURITY_REQUIREMENTS.md#sr-iss-03), [D-ISS-01](SECURITY_DECISIONS.md#d-iss-01), [CHECK-ISS-03](SECURITY_DECISIONS.md#check-iss-03).

Приоритеты учитывают последствия и условия возникновения угроз. Первые пять угроз входят в приоритетный набор. T-ISS-03 также покрывается решением; её приоритет нужно пересмотреть при частых сбоях, нестабильной связи с базой или появлении независимых хранилищ.
